# Wandering Lens — Documentary Site + AI Chatbot (starter project)

A learning-oriented starter project: a Next.js documentary/vlog site with a
RAG-powered (Retrieval-Augmented Generation) AI chatbot that answers
questions using YOUR content instead of guessing.

**100% free to run** — embeddings run locally via `sentence-transformers`,
retrieval is a hand-built NumPy vector store, and the chatbot's answers are
generated by a local LLM via **Ollama**. No API keys, no billing, no cost.

Placeholder content: 3 sample Bangladesh travel/culture episodes
(Sundarbans, Old Dhaka food, Cox's Bazar). Swap these for your real
scripts/transcripts later — the pipeline doesn't change.

## Project structure

```
project/
├── backend/           FastAPI + RAG chatbot API
│   ├── data/transcripts/   your documentary transcripts (.txt)
│   ├── ingest.py           chunks + embeds transcripts into ChromaDB
│   ├── main.py             the /chat API endpoint
│   └── requirements.txt
└── frontend/          Next.js website
    ├── app/                pages (App Router)
    ├── components/         React components (ChatWidget)
    └── lib/documentaries.ts   placeholder episode data
```

## How the AI chatbot actually works (read this first)

1. `ingest.py` reads your transcripts, splits them into chunks, converts
   each chunk into a vector ("embedding") using a free local model, and
   saves them into `store.npz` / `store_meta.json` — a tiny hand-built
   vector store using plain NumPy (no external vector database needed,
   and nothing to compile on Windows).
2. When a visitor asks a question, `main.py` embeds their question the same
   way, compares it against every stored vector with a dot product (cosine
   similarity), takes the top matches, and sends those chunks + the
   question to a local LLM running via **Ollama** - completely free, runs
   entirely on your own machine.

   Note: this NumPy approach is intentionally simple so you can see exactly
   what's happening. Real vector databases (ChromaDB, Pinecone, Weaviate)
   do the same core thing but add speed at scale (approximate search over
   millions of vectors), filtering, and persistence servers. Once you
   understand this version, swapping in a real vector DB later is a drop-in
   upgrade, not a new concept.
3. Claude answers using ONLY the retrieved chunks — this is what makes it
   accurate about your specific content instead of hallucinating.

This pattern is called **RAG (Retrieval-Augmented Generation)** — one of
the most in-demand AI engineering skills right now.

## Setup — Ollama (the free local LLM, do this first)

1. Download and install Ollama from **https://ollama.com** (free, all platforms)
2. Open a terminal and pull a model (one-time download, a few GB):
   ```bash
   ollama pull llama3.1:8b
   ```
   (If your laptop has limited RAM, try the smaller `qwen2.5:7b` or
   `llama3.2:3b` instead - just update `OLLAMA_MODEL` in `backend/.env`
   to match.)
3. Ollama runs as a background service automatically after install. Verify
   it's running:
   ```bash
   ollama list
   ```
   You should see your pulled model listed.

## Setup — Backend

```bash
cd backend
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

python ingest.py                # builds store.npz / store_meta.json from transcripts
uvicorn main:app --reload --port 8000
```

Visit http://localhost:8000 — you should see
`{"status": "ok", "chunks_loaded": N, "model": "llama3.1:8b"}`.

No `.env` editing or API key needed — it just works out of the box, as long
as Ollama is running.

## Setup — Frontend

```bash
cd frontend
npm install
cp .env.local.example .env.local
npm run dev
```

Visit http://localhost:3000 — you should see the homepage with 3 episodes.
Click into an episode and try the chatbot — ask something like
"What honey collectors are shown in the Sundarbans episode?"

## Learning roadmap (suggested order)

1. **Read `app/page.tsx` and `app/documentaries/[slug]/page.tsx`** — get
   comfortable with how Next.js routing and components work.
2. **Read `ingest.py` top to bottom** — this is the clearest explanation of
   chunking + embeddings you'll find, written specifically for this project.
3. **Read `main.py`'s `/chat` endpoint** — trace the full request path:
   question → embed → retrieve → prompt → Claude → response.
4. **Modify things**: add a 4th transcript, re-run `ingest.py`, ask the
   chatbot about it. Change `TOP_K` in `main.py` and see how answers change.
5. **Swap in real content**: replace the placeholder transcripts with your
   actual documentary scripts, update `lib/documentaries.ts`, re-run
   `ingest.py`.
6. **Deploy**: frontend → Vercel (free). Backend is trickier now since it
   needs Ollama running - see the "Deploying the free version" note below.
7. **Stretch goal**: try swapping `OLLAMA_MODEL` for different local models
   (llama3.2:3b vs llama3.1:8b vs qwen2.5:7b) and compare answer quality,
   speed, and RAM usage - great material for a "local LLM tradeoffs" blog
   post that ties into your networking/cloud background.

## Deploying the free version

Free-tier cloud servers (Render/Railway free tier) are usually too small/slow
to run a local LLM like Ollama well. Realistic options for a live public demo:
- Keep the AI chatbot running locally and demo it via screen recording or
  live during interviews, while the rest of the site (video content, pages)
  is deployed normally on Vercel.
- Or, if you want a fully public 24/7 chatbot later, swap `main.py`'s
  `ask_ollama()` call for a paid API (Claude, OpenAI, etc.) just for the
  deployed version, while keeping Ollama for local development - the RAG
  logic (chunking, embeddings, retrieval) stays identical either way.
